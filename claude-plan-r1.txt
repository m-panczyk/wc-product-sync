## 3. Why the current code is problematic (even though META_SYNCED is a constant)

- **No injection risk *today*, but the pattern is the hazard.** The value is currently a hardcoded constant, so there is no actual SQL injection at this moment. The problem is the *construction method*: string-concatenating a value into SQL. If someone later changes `META_SYNCED` to derive from an option, filter (`apply_filters`), or any dynamic source — common in WordPress plugins for extensibility — this line silently becomes a real injection vector with no warning at the call site.
- **Static analysis / coding-standard violations.** WordPress Coding Standards (`WordPress.DB.PreparedSQL` / `PreparedSQLPlaceholders`), Plugin Check, and most WP security scanners flag any `$wpdb->get_col()` on a concatenated string. This blocks clean linting and any wordpress.org submission audit, and it trains a bad pattern that gets copy-pasted to genuinely unsafe queries.
- **Defense-in-depth / consistency.** `$wpdb->prepare()` is the single documented safe path for building queries; using it unconditionally means reviewers don't have to reason about whether each individual value is "safe enough." It removes the per-line judgment call. Given this query feeds directly into a **destructive `$p->delete( true )` / `wp_delete_post( $pid, true )` loop** (permanent deletion during full sync), the query that selects the deletion set is exactly where you want the safe pattern, not a shortcut.
- **Correctness parity:** the fix changes nothing functionally for the current constant, so it is zero-risk to apply — pure hardening.
